# Code-fingerprint coverage: what a recorded run can and cannot be tied to

日期 2026-11-13 · 执行 tmh · 相关探针 `probes/audit_snapshot_stability.py`

这份文档回答一个具体问题：**给定一格已落盘的 `metrics.json`，它的代码状态能追到多细？**
答案是「取决于它落在哪个指纹世代，以及它的数值路径是否落在覆盖范围内」。这张表就是历史数据的可用性边界。

## 1. 指纹有三个世代

| 世代 | 起止 | 覆盖文件 | 哈希口径 | 计算时机 | 可信度 |
|---|---|---:|---|---|---|
| **A** | 至 `eb809ae`（11-13 18:51） | 5 | 原始字节 | **写 `metrics.json` 时** | ✗ 记录的是「收工那一刻盘上的代码」 |
| **B** | `eb809ae` → `0f4036d4`（21:30） | 5 | CRLF→LF（= git blob） | import 时 | 部分：时机对了，但漏文件 |
| **C** | `0f4036d4` 起 | 9 | CRLF→LF | import 时 | 当前世代 |

世代 A 的问题不是精度，是**语义**：训练期间任何人同步过代码，这一格的指纹就变成收工时的版本。B0 三个 seed 数值逐位相同却有三种指纹，就是这个造成的；`e89b23b0`、`1883b283` 两个查无 commit 的指纹同理。

世代 B 修了时机，但**覆盖范围仍然只有 5 个文件**——而今天冲刺新加的四个模块，一个都不在里面。

## 3. 边界结论

**① 冲刺四个模块（M2/M4/M5/M6）在 A/B 世代里没有任何覆盖。**
它们的机制代码分别写在 `cde.py` / `csr_pool.py` / `dpc.py` / `efr.py`，而这四个文件既不在指纹里、也不在代码锁里。所以「这几个 seed 跑在同一份代码上」这句话，对这四个模块**从构造上就无法从产物验证**——不是没查，是查不了。

**② 这不是同一类问题。**
`model_hc.py` / `data_hc.py` / 三个 FROZEN 文件也不在指纹里，但它们在**代码锁**里，锁是启动门（代码变了拒绝启动），所以它们有另一重保护。四个冲刺模块**两重都没有**。

**③ 因此「修好了记录器」≠「历史记录可信」。**
世代 C 让新格可以归因到文件，但补不回已经落盘的格。历史可用性只有两条路：重跑，或做逐位复现（`preds_md5` 相同）。静态审计（读 diff）是论证不是测量，翻不了案。

**④ M2 是侥幸的一个。**
`cde.py` 在跨快照审计里三次逐位相同（md5 `9de62ab1`），所以 M2 的 seed 在模块层面是一致的——**但那是审计出来的，不是指纹记出来的**。同一句结论，来源不同，可信等级不同。

## 4. 建议（未执行，需要和发射器协调）

把 `cde.py` / `csr_pool.py` / `dpc.py` / `efr.py` 加进 `run_hc.py` 的 `OWN`，锁升到 v16。
代价：需要重新生成锁索引（`code_lock.py` 需要 `git_sha`，3090 无 git，因此要在有 git 的机器上生成后同步），中途会打断一次发车。

**没有在冲刺中途做这件事**，因为它会改变启动门的基线，而四格前置门正在跑；指纹侧（世代 C）已经补上了覆盖，当前最紧的缺口是「历史格能不能用」，那只能靠复现解决，改锁不能。
