## 0. 一页摘要

**问题**：一个 1218 参数的「工况感知去趋势」模块（CADF），挂在 5 个公开 SOTA 的
RUL 预测骨干前面，能不能带来可重复的精度提升？

**做法**：5 骨干 × 2 子集 × 3 seed = 30 格。每格两条臂：V0（原骨干）与 +CADF。
两臂同数据、同划分、同超参、同轮数，唯一差别是模块。配对指标是逐发动机 RMSE 的均值，
`Δ = V0 − CADF`（正 = 模块更好）。

**结果**：**Gate 未达标（FAIL）**。10 个「骨干 × 子集」单元里 **9 个在第 1 步（三 seed 同号）
就判死**；剩下 1 个（`two_phase/FD004`）单元级四条全过，但**两个判定档位都放不下它**，
且它的 `p_null = 0.097`、是全部单元里误差最大的欠拟合基座，因此**不构成证据**。

**机制**：CADF 的全部输入都是 `x` 的确定性函数，**不引入 `x` 之外的新信息**；
它增加的是「特定形式的容量」，不是信息。这解释了为什么它对有足够容量的模型接近中性甚至有害。

**最强的一句话**：这不是「模块没测出来」，而是「按这个设计，它本来就不该普遍有效」。

## 1. 方法（CADF 到底是什么）

### 1.1 模块定义（代码可查）

对输入张量 `x ∈ R^{B×L×14}`（L 为窗口长度，14 个传感器通道）、掩码 `mask`、工况簇 `cluster ∈ {0..5}`：

```
b_t     = 该簇在窗口内前 K0 个有效点上的因果滑动均值      (mode='win')
delta_t = (x_t − b_t) ⊙ mask_t
e_t     = EMA(delta)_t ，逐通道可学习衰减 alpha           (mask 感知)
z_t     = [x_t , delta_t , e_t]                          (3D 维)
g_t     = sigmoid(gate(z_t))                             (逐通道门)
输出     = x_t + g_t ⊙ proj(z_t)
```

- `K0 = ceil(0.2·L)`：实测 L=50 → K0=10；L=45 → 9；L=30 → 6。
- `proj`、`gate` 都是 **zero-init**，所以初始化时输出**逐位等于输入**（恒等），
  这是本协议的核心契约：模块一开始不能改变任何预测。
- 参数量：`alpha(14) + proj(42×14+14) + gate(42×14+14) = 1218`。
- 挂载方式：只作用于传感器通道（多数骨干 0..13；`two_phase` 是 3..16），
  处理后原样回填，**骨干代码一行不改、权重全部参与训练**。

### 1.2 设计意图

工业 RUL 数据有强工况依赖（FD002/FD004 是多工况），作者的想法是：
用「同工况簇内的滑动均值」当基线，把慢趋势剥掉，让骨干看到更平稳的高频变化，
再让门控决定每个通道用多少这个修正。

### 1.3 一个必须说清的结构事实

`return x + g * proj(z)` 是**加性残差**，`x` 原样穿过。所以：

- 模块**不会**把趋势「减掉」——趋势一直在，它只能在上面加东西；
- 因此「剥掉趋势导致信息损失」这个解释在架构上**不成立**（这一点我们中途推翻过自己的说法）；
- `z` 的三个分量全是 `(x, cluster, mask)` 的确定性函数，**不引入任何外部信息**。

这一条是后面机制结论的全部基础，而且可以直接读代码验证，不需要实验。

单个「骨干 × 子集」单元要通过，四条**同时**成立：

1. **同号**：三个 seed 的 Δ 全部同号（3/3）；
2. **效应量**：`Δ̄ ≥ 0.45`（RMSE 单位，相对 C-MAPSS 的 RMSE 量级约 11–24）；

顺序很重要：反过来的话，`Δ̄ = −0.25` 的单元会被 CI 分支错归成「测不出（underpowered）」

档位：

- **Full（跨工况）**：同一骨干必须在 **FD001 与 FD004 同时**达标；
- **SC（单工况前端）**：**只认 FD001**；
- `k_pass ≥ 4/5` 才算 Gate PASS；`k_pass + n_undetermined < 4` 判 FAIL；否则 INCONCLUSIVE。

> 这里有一个**设计缺口**，我们如实记录、没有事后修补：这套分档**没有「只在 FD004 成立」

## 4. 执行过程中修掉的三个事故（全部留痕，未删文件）

### 4.1 `ffve` 六格全崩：断言写错，不是模块违规

首轮 6 个 `ffve` 格全部报 `CADF is not the identity at initialisation`。
查下来根因是**测试写法**，不是 CADF：

- `ffve` 的 forward 里有 `reparameterize()`（VAE 重参数化），**每次前向都采样**，
  `eval()` / `no_grad()` 都拦不住；
- 实测：关掉 CADF 连跑两次，全网络输出差 **0.2697**；`aidgn` 同测差 **0.0**；
- 而 `cadf(x) == x` **逐位为真（max diff 0.0）**。

所以旧断言（比较两次全网络输出）只对确定性骨干成立，对 `ffve` 是**测试假阳性**。
修法：把断言改到**模块边界**（`torch.equal(cadf(x), x)`，逐位），
并把 `backbone_deterministic_in_eval=False` 记进该格的 `cadf.json`。
判据、CADF 实现、预注册都没动。修完 6 格重跑，全部通过。

### 4.2 `dual_mixer/FD001/s303` 采样器用错：`anchor_tiled` → `exact`

`dual_mixer` 的上游负采样器会构造 `[B, K+1, L, D]` 的候选张量。
早期版本把 anchor 的 mask/cluster **平铺** K+1 次（`anchor_tiled`），
后来改成按负样本真实下标重算（`exact_negative_indices`）。全批只有 1 格用了旧写法。

修完重跑，该 seed 的 Δ 从 **+0.0752 → +0.3873**（差 0.312），
该组 `Δ̄` 从 **−0.1486 → −0.0445**。旧格移入 `out_b/_superseded/`，没有删。

### 4.3 命名坑：`within_noise` 其实是 `not passes`

判定记录里有个字段叫 `within_noise`，代码里就是 `within_noise = not ok`。
**它不是噪声检验**，只是「这一票没过」的另一种说法。名字会诱导人当统计量引用。
后续版本改名为 `not_passes`；因为冻结产物不能覆盖，做法是**新旧两版各跑一次、逐字段 diff**：

- 差异总数 **20** = 10 个单元 ×（删 1 键 + 增 1 键）；
- 全部是**键名**，**值逐个相同**；
- `verdict` / `k_full` / `k_sc` / `tier_state` / `power` 全部一致。

## 6. 唯一一个通过单元判据的格：`two_phase/FD004`

必须单独交代，否则会被问「唯一通过的那一票去哪了」。

### 6.1 它确实过线

- 三 seed：**+0.8032 / +0.7087 / +0.8470**，全正；
- `Δ̄ = +0.7863 ≥ 0.45`；
- 胜率 **0.60 ≥ 0.60**；
- CI **[+0.1698, +1.5114]**，**不含 0**；
- 单元级 `passes = true`。

### 6.2 为什么不计票

- **Full 档**要求同一骨干在 **FD001 与 FD004 同时**达标，而 `two_phase/FD001 = −0.1062`；
- **SC 档**按预注册**只认 FD001**。

**两档都放不下它。** 这是冻结设计的缺口（这套分档没有「只在 FD004 成立」的位置，
而 SC 正好是它的镜像），**不是执行错误，我们也没有事后改判据**。
下一版预注册应当补一个对称档，或明确写「单工况前端是有意为之」。

### 6.3 为什么它仍然不能当证据

四条理由，缺一都会导致误读：

1. **多重比较**：10 个单元里出现 1 个 `p_null = 0.097` 的结果，是零假设下的**期望值**
   （10 × 0.097 ≈ 1）。它不显著，只是看起来像。
2. **欠拟合基座**：`two_phase` 在 FD004 上的绝对误差是 **22.94–23.44**，
   而其余 9 个单元是 **10.37–14.89**。它是全场最差的一个基座。
   「模块帮了一个自己拟合不了的模型」是合理的解释，但**只有一格**。
3. **`t = 19.27` 不是功效证据**：`t(2)` 恰恰是 v7 从判据里删掉的检验（n=3 没有功效）。
   临界值 4.30 这么高，意味着 t 显著主要反映**三个 seed 挤得极紧**，
   不反映跨发动机可推广性。跨发动机只有 CI 和 MDE 能回答。
4. **它不能外推**：一个在欠拟合基座上取得的正效应，不能推出「模块对正常工作的骨干也有效」——
   而后者正是 9 个失败单元给出的答案。

### 6.4 这条的定位

**「唯一过单元判据、但两档都无处安放、且不构成证据」**——四个限定词一个都不能少。
任何把它写成「唯一有效」的表述都是错的。

## 7. 机制：为什么它不该普遍有效

### 7.1 核心论证（代码可验证，不需要实验）

`z = [x, delta, e]`，其中：

- `b` 是 `(x, cluster, mask)` 的确定性函数（同簇前 K0 个有效点的因果均值）；
- `delta = (x − b) ⊙ mask`，也是确定性函数；
- `e = EMA(delta)`，可学习衰减但输入仍是 `delta`；
- `x` 本身原样进 `z`。

**所以 `z` 不携带任何 `x` 之外的信息。** 模块能做的只是「在已有信号上加一个可学习的
线性变换」，它增加的是**容量**，不是**信息**。

这直接给出预测：

- 对**已有足够容量**的模型（5 个 SOTA），外挂一条同信息量的分支 ≈ 重复劳动，
  Δ 落在 0 附近、符号随 seed 翻——**实测正是如此（9/10）**；
- 对**自己算不出这条变换**的模型，外挂才有增量——**唯一支持它的就是 `two_phase/FD004`
  那个欠拟合基座，只有一格，不足以立论**。

### 7.2 两个被否掉的替代解释（都留了证据）

**解释 A：「剥掉趋势 → 只剩高频噪声 → 丢信息」。**
架构上不成立：`return x + g*proj(z)`，`x` 原样穿过，趋势一直在。
而且它自己的预测被证伪：`ffve` 的 `‖x−b‖/‖x‖` 最小（0.19–0.22，即「剥得最轻」），
按这个逻辑它该最好，实测它反而是不差的之一（−0.048 / −0.316），不构成支持。

**解释 B：「容量依赖」（参数量越小的模型越受益）。**
两个量化代理都不支持：

| 骨干 | 骨干参数 | CADF | 相对开销 | 组 Δ̄ 排序 |
|---|---:|---:|---:|---|
| dual_mixer | 64123 | 1218 | 1.86% | −0.045 / +0.110 |
| aidgn | 30070 | 1218 | 3.89% | −0.362 / +0.273 |
| fcstgnn | 27293 | 1218 | 4.27% | −0.166 / +0.218 |
| two_phase | 24289 (FD004) | 1218 | 4.78% | **+0.786** |
| two_phase | 12969 (FD001) | 1218 | 8.58% | −0.106 |

- **绝对参数量**：`two_phase` 只有 12.9k（比 51k 的 B_min 还小）却无收益 → 反序；
- **相对开销**：最高的 `two_phase/FD001`（8.58%）排第四，最低的 `dual_mixer`（1.86%）
  一正一负 → 完全不单调。

**结论：「容量依赖」不能写进论文。** 准确写法是「原因未定，参数量不能解释排序」。

### 7.3 探针（补充，不作为主证据）

- `‖b‖/‖x‖` = **0.79–0.93**，`‖x−b‖/‖x‖` = **0.19–0.54** → 可剥的量确实大；
- 线性 ridge 探针（展平窗口，CPU）：`ridge(x)` 20.5–21.3，`ridge(x−b)` 20.96–23.2，
  `ridge(b)` 25.8–27.4 → **`b` 幅度大但信息量低；`delta` 单独当特征只比 `x` 差 2%–10%**。
- 这两个数字只说明「`delta` 这条分支本身不是没用」，**不能**说明模块丢了信息
  （见 §7.2 解释 A）。
- `‖proj‖` 长到 **0.99–5.29**、`‖gate‖` **1.61–9.50** → 模块**确实被激活了**，
  不是「梯度没过去 / 模块没训」。

### 7.4 排序不可归因

10 个组里 **9 个 `|t| ≤ 2.83`**（df=2 临界 4.30），即组间差异没有一个能和 seed 噪声区分开。
在这个前提下，任何「轴」（参数量、相对开销、有没有 LayerNorm、平滑不平滑）都只能拟合噪声。
**找到一个轴才是危险的**，因为那意味着给随机排序编了个故事。

## 10. 给下一轮的教训（比本轮结论值钱）

**要提升大模型，必须加信息，不能重编码。**

CADF 的全部输入都来自 `x`，所以它注定只能帮到「算不出这条变换」的模型。
下一轮如果还要做模块，第一个问题必须是：

> **它引入了 `x` 之外的什么信息？**

答不出来，就不该开工。
